# AI 编程助手工作规则（AGENT_RULES）
版本：1.0  
适用对象：DeepSeek（DS）及其他参与本项目的 AI 编程助手  
优先级：本文件是项目级工作约束。若与临时任务提示冲突，除非用户明确授权，否则遵守本文件。

## 1. 工作目标

你不是一次性生成整个项目，而是以小步、可验证、可恢复的方式协助开发一个 Windows 优先、本地优先的个人番剧管理软件。

优先级依次为：
1. 正确性与用户数据安全。
2. 保持项目可构建、可运行。
3. 完成本轮明确指定的范围。
4. 可测试、可维护。
5. 视觉和体验改进。
6. 后续扩展能力。

不要为了“架构完美”无限重构，也不要为了快速完成而跳过数据保护和测试。

## 2. 每次任务的固定流程

每次收到开发任务，按以下步骤执行：

### 第一步：确认任务边界
用不超过 5 条列出：
- 本轮目标。
- 明确要修改/新增的内容。
- 本轮不做的内容。
- 预期验证方式。
- 任何阻塞性不确定问题。

如果没有阻塞性问题，直接继续，不要因为非关键细节反复向用户提问。

### 第二步：检查现状
- 先检查当前分支、工作区状态、项目结构和相关文件。
- 先运行与本任务相关的现有测试或构建，建立基线。
- 如果工作区已有用户改动，不得擅自覆盖、重置或删除。
- 不要为了熟悉项目而反复读取所有文件；优先阅读任务涉及的模块和其直接依赖。

### 第三步：制定最小计划
列出 3–7 个可执行步骤。每一步都应能通过文件变更、测试或可见结果验证。
只实现当前任务，不提前实现后续阶段。

### 第四步：小批量修改
- 优先做最小、局部、容易审查的改动。
- 每一轮集中处理一个问题或一个紧密相关的小功能。
- 避免同时重写 UI、数据库、架构和依赖。
- 不要无理由格式化或重写大量无关文件。
- 新增依赖前先说明必要性；能用现有依赖解决时不要新增依赖。

### 第五步：验证
按优先顺序运行：
1. 与改动直接相关的测试。
2. lint/typecheck。
3. 完整测试。
4. 构建。
5. 必要的手工验收步骤。

如命令失败，先读取错误输出并定位原因，不要盲目重复执行同一命令。

### 第六步：总结并停止
按本文件第 9 节的固定格式报告。报告完成后停止，等待下一条任务。不得自行继续实现下一个阶段。

## 3. 防止循环思考与无效调试

以下规则必须遵守：

### 3.1 同一问题的重试上限
- 同一个失败原因最多进行 3 轮有实质差异的修复尝试。
- 每次重试前必须写明：上一轮失败原因、这次改动的假设、如何验证。
- 不允许连续重复同一命令、同一提示词或同一代码修改，却期待不同结果。
- 如果 3 轮仍未解决，停止修改，提供已尝试方案、错误信息摘要和需要用户决定的选项。

### 3.2 设定调试时间/步骤边界
- 简单问题：先尝试最小修复并验证。
- 复杂问题：先复现，再缩小范围，再修复。
- 不要因为一个非阻塞警告而反复修改整个架构。
- 不要为了追求零警告而引入高风险改动。
- 如果问题来自外部服务、网络、权限、环境或工具缺失，应明确指出，不要把它误判成代码错误无限排查。

### 3.3 防止方案发散
- 对一个功能最多提出 2–3 个可行方案，然后明确推荐其中一个。
- 用户已选定技术栈或产品决策时，不要反复推翻；只有发现明确的技术障碍或重大风险时才提出变更。
- 不能用“更优雅”“更先进”作为大规模重写的唯一理由。
- 不要重复输出冗长的思考过程。给出简洁计划、实际行动、验证结果和结论即可。

### 3.4 停止条件
遇到以下情况应暂停并报告，而不是继续猜测：
- 需要破坏或覆盖用户数据。
- 需要删除/重置数据库、清空目录、执行不可逆命令。
- 需要改变核心技术栈、数据库主结构或项目范围。
- 需求之间有实质冲突，且无法安全采用保守默认值。
- 依赖、API 或外部资料的行为无法验证，继续实现会产生高风险。
- 同一问题已达到 3 次实质不同的失败尝试。

## 4. 代码和项目范围约束

- 未经用户明确同意，不得更换 Tauri 2 + React + TypeScript + Vite + SQLite 的技术基线。
- 当前阶段只做 Windows 桌面端；不实现手机端、账号系统、云服务或自动同步。
- 当前版本不内置播放器；本地视频由 Windows 默认关联播放器打开。
- 打开视频不自动标记已看，不追踪实际播放时长。
- 观看统计基于已看集数和标准单集时长；未知时长不得随意填默认值。
- 观看年度/季度归类依据用户填写的首次观看日期，不依据记录创建日期。
- 外部元数据不得覆盖个人观看状态、观看日期、评分、标签、备注、收藏和手工锁定字段。
- 本地文件移动或丢失不得删除作品、集数和观看历史。
- 扫描、导入和批量操作优先采用非破坏性策略；高影响操作必须确认并尽可能可撤销。
- 不要提前实现未来手机同步的实际功能；只保留稳定 ID、时间戳和清晰模块边界等必要扩展点。

## 5. 数据库与用户数据保护

- 数据库结构变更必须新增版本化迁移，不得只修改初始化 SQL。
- 迁移必须考虑已有数据和失败回滚，并提供测试。
- 不得擅自删除数据库、重置迁移历史或清空用户数据。
- 关键多步写入使用事务。
- 使用参数化 SQL，不得将用户输入直接拼接进 SQL。
- 删除/归档作品、季、集或文件关联前，检查关联数据并向用户说明影响。
- 备份/恢复功能必须有校验和错误处理。
- 不得把用户个人数据发送到任何远程服务；当前版本没有云同步需求。
- 不要在日志或错误报告中无必要地输出完整本地路径、备注等个人信息。

## 6. 参考项目：PotatoVN 与 The-Order

这两个项目是**产品研究与设计参考**，不是要求复制其代码。

### 可参考的方面
- 作品库/书架的组织方式。
- 详情页的信息层级和导航方式。
- 扫描、识别、匹配、人工确认的工作流。
- 外部数据库资料导入与本地数据管理的分离。
- 作品资料、个人状态、文件索引之间的边界。
- 对识别结果进行人工核对和纠错的体验。
- 空状态、错误提示、批量操作和设置页的交互。

### 参考流程
1. 先查看项目公开 README、截图、文档和功能说明。
2. 把值得借鉴的具体功能记录到 `docs/REFERENCE_RESEARCH.md`，说明“参考点—本项目的应用方式—差异”。
3. 只借鉴适合本项目目标的思路；本项目的需求和架构文档优先。
4. 不要为了模仿参考项目而引入不需要的功能或依赖。
5. 不要复制其品牌、图标、专有素材或大段 UI 文案。
6. 不要直接复制代码。若用户明确要求复用代码，必须先确认对应文件的许可证、版权声明、依赖许可证和分发义务，再提出合规方案。
7. The-Order 公开仓库曾标注 AGPL-3.0，PotatoVN 曾标注 Apache-2.0；在任何代码复用前必须重新核对当前仓库中的许可证文件和具体代码来源，不能只凭本文件中的说明作法律结论。
8. 如仅研究交互和产品思路，不需要将参考项目源码引入本仓库。

## 7. 外部 API 与联网约束

- 外部 API 先查官方文档，确认认证、限流、字段、可用性和使用条件。
- 不要虚构 API 字段、端点或成功响应。
- 网络请求应有超时、错误映射和必要的缓存。
- 单个 Provider 失败不能阻断核心本地功能。
- 不要绕过站点登录、验证码、访问控制或站点规则。
- 对不确定的 API 行为，先实现接口和 mock 测试，再在真实接入阶段验证。
- 不要将密钥写入仓库或普通配置文件。

## 8. Git、文件和命令约束

- 任务开始时检查 Git 状态。
- 不得擅自执行 `git reset --hard`、强制 checkout、清理用户改动或重写公共历史。
- 不得擅自执行危险删除命令、清空目录或覆盖未知文件。
- 不得在未检查现状时生成大量文件。
- 不得修改与任务无关的文件。
- 每个阶段完成后，建议用户创建一个语义清晰的 Git commit；如果用户没有要求，不要擅自推送远程仓库。
- 不得声称“测试通过”而没有实际运行测试。若工具不可用，应明确标记“未运行”，不能伪造结果。

## 9. 每次任务的最终报告格式

每轮结束必须使用简洁格式：

1. **本轮目标与结果**：完成/部分完成/阻塞。
2. **改动文件**：列出关键文件及作用。
3. **实现说明**：说明重要设计决策。
4. **验证结果**：列出真实运行的命令和结果；未运行的明确标注。
5. **风险与未解决问题**：只列实际存在的问题。
6. **手工验收步骤**：给出用户可以复现的步骤。
7. **建议下一步**：只建议一个下一步，不自动执行。

如果任务未完成，明确指出未完成部分，不要用模糊措辞伪装完成。

## 10. 新会话/上下文压缩时的恢复规则

如果上下文被压缩或开启新会话：
1. 阅读 `README.md`、`AGENT_RULES.md` 和当前任务阶段的相关文档。
2. 查看 Git 状态、最近提交、当前测试结果和 TODO。
3. 以仓库现状为准，不要假设此前计划已经实现。
4. 先报告当前阶段与未完成事项，再继续当前任务；不要重做已完成工作。
